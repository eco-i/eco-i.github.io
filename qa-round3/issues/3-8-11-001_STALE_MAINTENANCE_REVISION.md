## 원본 결함 직접 재현 (실제 QA JS와 지연 mock RPC)
1. 관리자 정비 draft에 2028-11-01 B조 `야` 저장 요청 시작.
2. 저장 응답보다 먼저 `get_maintenance_schedule` 조회 시작. 서버가 오래된 revision `0` 상태를 조회했다고 가정하고 응답을 보류.
3. 저장 RPC가 revision `1`로 성공, 브라우저 `maintenanceSchedule.revision=1` / draft baseline=1.
4. 느린 조회가 revision `0`으로 완료되면 원본 코드는 최신 캐시를 **revision 0으로 되돌린다**. 저장된 B조 야간 override는 캐시에서 소실되고 편집 baseline은 revision 1이어서 stale 상태가 된다.
5. 별도의 순서로 현재 상태 rev2 조회가 먼저 끝나고 그보다 옛 rev1 저장 응답이 나중에 도착하면 원본 저장 성공 경로가 rev2 → rev1로 역행하고 성공 토스트를 표시함도 재현.

두 경우 모두 **서버의 실제 기록을 삭제한 것은 아니고 브라우저가 최신보다 오래된 편성/개정 상태를 채택하는 문제**. 동일한 응답 순서/개정번호 정합성 결함으로 1종 계상.

## 수정
- `loadMaintenanceSchedule()`: 서버 조회 결과의 revision이 현재 캐시보다 낮으면 **적용 거부**, 최신 캐시 유지, 오류 대신 기존 캐시 사용 가능상태 보존.
- `maintenanceSave()`: 오래 지연된 저장 응답보다 높은 revision을 이미 조회해둔 경우 **더 높은 버전 보존**. 저장 완료 후 최신 상태를 UI에 표시하며 다른 탭 변경을 확인했다는 별도 안내.
- 저장·조회가 겹치는 중 낮은 revision의 조회 **오류 응답**이 마지막에 도착하더라도 이미 성공한 저장의 `maintenanceReady=true`를 false로 돌리지 않도록 조회 시작 시 revision 기록.
- 첫 수정안에서 저장 완료와 동시에 모든 이전 조회를 폐기했더니 더 최신 rev2까지 폐기하는 QA 회귀가 발견됨. 해당 과잉 무효화는 운영 반영 전 철회하고 **revision 비교 우선**으로 조정함. QA 수정안 회귀 오류이며 별도 운영 제품 결함으로 계상하지 않음.
- 앞선 `3-8-8-001` 저장 중 잠금·`3-8-9-001` 재조회 도중 편집 보존·`3-8-10-001` 세션 별 저장 세대 번호 보호는 유지.
