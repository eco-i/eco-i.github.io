## 재현
1. 관리자가 ‘최신 설정 다시 불러오기’를 눌러 수동 조회 R1 시작. R1의 모의 서버 응답을 지연.
2. 실시간 갱신/달력 로딩에서 `loadMaintenanceSchedule()` R2 시작. 이 함수는 `maintenanceLoadSeq`를 증가시켜 R1을 오래된 요청으로 처리.
3. R2에서 새 개정번호 3 및 새 기간 ‘서버 3’을 성공적으로 수신, `maintenanceSchedule.revision=3`, `maintenanceReady=true`.
4. R1이 나중에 끝나면 소유권 검사로 반환값 false. 기존 `maintenanceReloadEditor()`는 이를 **항상 서버 조회 실패로 오인**해 빨간 오류 토스트를 보여주고, 편집 draft·baseline을 개정 0으로 남김.
5. 실제 `main`, QA 양쪽의 정비 JS 함수와 보류한 mock RPC로 재현. 서버 자체 오류 또는 직원 기록 변경이 아님.

## QA 수정
- 수동 조회 시작 당시 `maintenanceLoadSeq`를 캡처.
- 반환 false일 때 동일 요청이 아직 최신이면 진짜 오류 메시지 유지.
- 이후 더 새로운 요청이 성공하여 `maintenanceReady=true`이면 그 **공식 최신 캐시를 재조회 성공으로 취급**해, 편집 중 내용이 바뀌지 않은 경우에만 수동 편집창 갱신.
- 이후 요청이 아직 진행 중이거나 실패했다면 서버 장애라고 단정하지 않고 **‘다른 최신 정보 조회 진행 중…’ 정보 안내**, 재시도 가능.
- 이전 3-8-9의 편집 도중 작성내용 보존·모달 종료·세션 변경 가드 유지.
