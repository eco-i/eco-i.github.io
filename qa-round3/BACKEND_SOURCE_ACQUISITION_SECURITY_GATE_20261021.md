## 2. 공개 GitHub·Actions 정보유출 금지
1. **실제 운영 서버 SQL 원문, 함수 body, RLS 조건식·GRANT 전체, 사용자/직원 데이터, Auth 테이블 덤프, PIN·패스워드·해시·토큰·API 키·연결 문자열은 이 공개 저장소의 어느 브랜치에도 업로드하지 않는다.** SHA나 파일 이동으로 기존 Git 히스토리 노출을 해결할 수 없다.
2. GitHub Actions 로그, artifact, PR, Issue, 커밋 메시지 및 테스트 실패 출력에도 원본/비밀을 넣지 않는다. 테스트 저장물은 synthetic 데이터만.
3. DDL은 데이터 없이도 함수 본문에 민감한 상수·보안정책이 포함될 수 있으므로 공개 가능하다고 자동 간주하지 않는다.
4. `QA` 프로젝트와 `운영` 프로젝트는 계정·데이터·자격증명·프로젝트 참조·브라우저 origin을 분리한다. 절대 운영 키를 QA workflow secret에 재사용하지 않는다.

## 3. 원본 확보 우선순위와 승인
- **A (최선):** 개발자가 관리하는 신뢰 가능한 기존 *비공개* 스키마/migration/함수 원본이 있는지 먼저 확인. 데이터 백업이 아닌 **원본 코드**와 버전·적용 순서·변경 이력을 확보하며 출처를 명기.
- **B (승인 필요):** A가 불가능하면 **운영 Supabase에서 메타데이터/DDL만 읽기 위한 사전 별도 명시 승인**을 먼저 받는다. 최소 권한 read-only 점검을 설계하되 승인 전 연결·실행·시크릿 등록 금지.
- B 승인을 받아도 **운영 직원 데이터/지문/세션 내용/Auth 사용자 목록/비밀번호/PIN/SQL 실행에 따른 DML·DDL 변경은 금지**. 함수 본문·권한 정책 안의 보안 비밀을 별도로 검토한다.
- 실제 원본 DDL은 접근통제되는 비공개 보관 경로를 마련하고 노출 검토한 후 사용. 공개 저장소에는 `function name`, `출처 확인 여부`, `재현 가능 여부` 등 비민감 상태만 기록한다.
