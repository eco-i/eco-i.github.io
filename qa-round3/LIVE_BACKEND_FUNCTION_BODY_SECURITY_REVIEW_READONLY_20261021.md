# 근무모아 — 운영 서버 기존 함수 구현·스키마·권한 읽기 전용 검토 (2026-10-21)

> **승인 범위:** 사용자가 별도 승인한 운영 Supabase의 기존 함수 정의, 공개 스키마의 테이블 구조, 실행권한·RLS 구조에 대한 SELECT 메타데이터/DDL 조사. **실 직원·근태·PIN·사진·세션 데이터 행 미조회, 업무 RPC 호출 0, DDL/DML 0, 운영 배포 0.**
>
> 이 저장소는 PUBLIC이다. **함수 본문, 내부 권한판정·보안정책 원문, 서버 비밀, 직원정보, 실제 데이터를 여기에 적지 않는다.** 이 문서는 비민감 판정·시험 조건만 담는다.

## 1. 실제 분석 범위와 신뢰 경계

- 라이브 DB의 `pg_catalog.pg_proc`와 정의 조회 기능을 통해 **기존 업무 함수 26개**의 구현을 읽기 전용으로 분석하고, 추가로 **공통 내부 보조 함수 19개**를 호출 관계·잠금·세션검사 관점에서 확인했다. **둘 다 이미 설치된 구버전/보조 함수**이며, 누락된 최신 RPC 26개와 혼동하지 않는다.
- `pg_class`, `pg_attribute`, `pg_constraint`, `pg_policy`, PostgreSQL 역할별 privilege 메타데이터를 조회했다. 공개 업무 테이블 **27개 모두 RLS 활성화** 상태임을 확인했다. 선택한 업무 관련 테이블 19개에서 **139개 컬럼의 구조만** 확인했다. **한 건의 실제 행도 읽지 않았다.**
- 클라이언트의 직접 테이블 쓰기권한보다, 제한된 서버 RPC에서 세션·권한 검사를 수행하는 방식에 크게 의존하는 구조다. **RLS 활성화 그 자체로 SECURITY DEFINER 함수의 안전성을 증명하지 않는다.** 정확한 RLS 정책 내용·함수별 EXECUTE 허용역할·세션 검증 세부 조건은 공개하지 않는다.
- 조사된 기존 함수는 역할 상승 실행 경계를 포함한다. 확인 대상 기존 함수의 서버 search_path 설정 여부를 점검했으나, **검색경로 설정만으로 권한 우회가 불가능함을 증명한 것은 아니다**.
- 모든 판단은 소스 존재·형태·정적 참조에 관한 것이다. 실제 비정상 요청, 동시 쓰기, 강제 로그아웃, DB rollback, 계정 접근 통합시험을 **수행하지 않았다**.

## 2. 기존 구현에서 확인한 보존 필수 기능

| 업무 흐름 | 읽기 전용 구현 확인 사항 | 최신 함수에서 추가 검증할 필수 사항 |
|---|---|---|
| 로그인·직원 권한·관리자 인사변경 | 기존 공통 세션 판정 및 관리자/업무 가능 계정 검사, 인사 변경 이력·관련 레코드 보호 흐름이 설치되어 있음 | 모든 최신 함수에서 동일한 현재 세션/계정상태·업무 가능기간/관리자 여부의 **서버 측** 검사, 여러 창의 인사 변경 시점 경합 |
| 직원 메모·연차·장기근속 | 기존 개인별 데이터 접근을 서버 세션과 연결하는 함수가 설치되어 있음; 해당 구버전에는 최신 프런트의 `p_expected` 비교 계약이 없음 | 업데이트·삭제 시 대상 직원 소유권과 기존 행의 변경버전(CAS)을 **원자적으로** 비교하고, 충돌 시 초안·기존 행 보존 |
| 휴일근무 | 기존 날짜 적격성·계정 쓰기 가능 여부·근무시간 산정 보조 절차가 존재함 | 현재 유효한 조/일근/휴무 규칙과 수정 대상 `id`+`updated_at` 비교, 다른 세션 선행변경을 덮어쓰지 않는지 검증 |
| 관리자 인사배치·계정·PIN | 서버 관리자 권한 판정·기존 이력보존/잠금 흐름이 존재함 | 요청 전/실행 중 revision 일치, 최종 관리자 보호, 계정 변경과 세션 철회의 경합, PIN 초기화의 변경 전후 비교 |
| 백업·미리보기·복원·초기화 | 기존 백업 생성·데이터 형식 검증·업무 테이블 읽기/쓰기 잠금·감사기록의 분리된 보조 절차가 존재함 | **미리보기→확인→실행 사이의 revision 변경을 원자적으로 거부**하고, 전체 성공 또는 전체 롤백, 복원 시 식별자/스키마/직원 관계 보존 |
| 회사 일정 | 서버에서 관리자 검증과 일정 변경·감사 흐름이 존재함 | 동일 행사 ID와 `updated_at` 비교 및 중복·기간 충돌 검증; 삭제 직전 데이터 버전 비교 |
| 보안·감사·Realtime | 기존 보조 함수에 이력/변경 신호 관련 경로가 존재함 | 이력 불변성, 수정자/대상 구분, 메시지 중복·실패 및 다른 세션 최신화 처리 |

**중요:** 여기의 ‘존재’는 코드 구현의 정적 특징에 대한 판정으로, 특정 우회 공격의 부재나 동시성 안전성 PASS가 아니다. 실제 운영 내 함수 소스는 비공개로 유지한다.

## 3. 26개 복구 계약에 반영할 우선 검증 게이트

- [26종 정확 이름/인자 계약표](e2e/ci/missing-rpc-recovery-contracts.json)를 기준으로 작업. 서버 설치명 26개가 빠져 있으며, 유사한 구버전이 있는 22종 가운데 19종은 최신 인자명이 다르고 3종만 인자명이 일치한다. 최신 원본 **확보 0**; 미설치 상태는 이번 읽기만으로 해결되지 않는다.
- **P0 (직원 전체 기록을 변경할 수 있는 기능):** 관리자의 인사발령·인사 이력복구·계정정지·PIN 초기화·전체 데이터 초기화·백업복원. 각각 사용 불가/권한 없음/동시수정/중간 실패/관리자 자기보호/유효하지 않은 payload에서 *기록을 전혀 바꾸지 않아야 한다*.
- **P1 (개인 업무기록):** 메모 3종, 휴일근무 5종, 회사행사 2종, 연차·장기근속 각 1종. 각 기능의 본인 외 접근, 이전 수정본으로 덮어쓰기, 원치 않는 삭제, 불완전한 오류 알림/초안 손실 방지 시험이 필요하다.
- **미리보기 RPC:** 읽기 결과만 반환하고 기록을 바꾸지 않아야 한다. 후속 적용 시에는 당시의 개정번호와 현재 개정번호를 DB 트랜잭션 안에서 비교해야 하며, 미리보기 성공만으로 곧바로 복원 실행을 승인할 수 없다.
- **서버 구현 기원:** 이번 분석에서 확인한 구버전 서버 소스는 신규 구현을 검토할 때 참고할 근거이지, 누락된 최신 RPC의 **정본/설치 가능 스크립트가 아니다**. 공개 저장소에 원본 본문 저장 금지. SQL 이름만 바꾸는 forwarding 함수 생성 금지.
- **합격 조건:** 운영 직원과 무관한 **독립 QA DB**에 전체 의존 schema/실제 구현을 설치하고, PostgREST·세션·EXECUTE 권한·RLS·2계정 CAS·백업 rollback을 실증해야 한다. 운영 서버 DDL/DML은 **별도의 최종 승인 전까지 금지**.

## 4. 기록과 현재 상태

- 이번 작업은 **사용자가 승인한 기존 함수 본문·정책/스키마의 추가 읽기**만 수행했다. 데이터 행/계정·세션 레코드 조회, 실 RPC 호출, 스키마/직원정보 변경 **0**.
- 공개 GitHub에 남기는 것은 **위 테스트 계획 및 범위한정 메타데이터 결론**뿐이다. 함수 원문/정책식/보안 상태의 세부 취약 경로는 공개하지 않는다.
- 공식 마지막 완료 **3-8-53**, 다음 **3-8-54 미시작·BLOCKED**, 3차 제품 신규 결함 **37종 유지**.
- 정적 RPC 계약 유지 CI는 PASS이나, **실제 서버 26종 미설치 릴리스 차단은 RED 유지**. 전체 E2E **NOT CLEAN**, 운영 `main`·실제 직원 DB·운영 SQL 변경 없음.

**실질적인 다음 일:** 이 분석에서 확보한 안전 요구를 **비공개 구현 설계 문서**와 독립 QA 서버 기능의 정본으로 바꿔야 한다. 실제 구현 SQL을 새로 작성하거나 별도 QA 프로젝트/과금/운영 반영하는 것은 자동으로 승인된 범위가 아니다.
