## 1. 이번 작업에서 실제로 추가 확인한 사실
1. 운영 `main` HEAD `6c784210e048426f18a486d5602652626d97574d` HTML blob `5553a1d319e3ab7ff4dd6bb8ee7d995657112698`의 26종 **직접 RPC 호출 31개소**를 다시 정적 대조했다.
2. 현행 공개 GitHub **`db/migrations/*.sql` 16개를 원본 blob 기준 전수 검사한 결과**, 이 26종 함수 이름의 정의뿐 아니라 이름 직접 출현 자체가 **0종**이었다. 따라서 현재 GitHub의 기존 운영용 마이그레이션만으로 최신 26종을 설치할 수 없다.
3. 접근 가능한 **2026년 9월 비공개 SQL 보관본 6개**를 읽기 전용 이름 검색했지만 **정확한 26개 함수 이름에 대한 직접 일치 0종**. 이는 6개 문서의 검색 결과이지 *모든 과거 SQL의 부재 증명*이 아니다. 비공개 파일/원본 본문 공개 반출 0.
4. 이전 사용자 승인 범위 내에서 운영 Supabase `pg_catalog.pg_proc`를 **SELECT 읽기 전용으로 다시 조사**해, 프런트에서 부르는 최신 이름 26종의 명칭은 여전히 설치되어 있지 않고(기존 54/26 snapshot), 동일한 기본 이름을 가진 구버전 함수가 설치돼 있는지, 함수 입력 인자명만 비교했다. **업무 RPC 호출·DML/DDL·실직원 행 조회 0**.

## 3. 우선 복구 순서와 확인 조건
1. **최고위험 P0:** 관리자 PIN 초기화, 관리자 인사·계정 상태, 인사이력 되돌리기, 데이터 초기화/복원/안전백업 기능. revision/CAS와 권한을 생략하면 기존 기록 오염 또는 타인 데이터 접근 위험. **읽기전용 preview 함수 포함해 독립 QA에서 원본 설계/불변 조건 검증 필수**.
2. **P1 업무 필수:** 휴일근무 등록/삭제, 회사일정 변경, 연차 기준, 장기재직, 개인 메모/삭제. 사용자 초안과 DB 변경 후 UI 결과의 동등성, CAS 충돌/중복 저장/권한탈취 시험 필수.
3. **서버 원본 확보 경로:** 먼저 합법적으로 접근 가능한 원본 migrations·비공개 백업·이전 설계 문서의 *최신 SQL*을 확보. 구버전 함수는 원본 이해용 후보이지 최신 원본이 아님. 없으면 새 구현이 필요한 기능을 계약표에 따라 보안 리뷰하며 설계한다. 이 단계는 **기존 기능 손상 위험 때문에 자동 원형 보간·SQL 조립/실행으로 처리하지 않음**.
4. **완전 독립 검증 경로:** 직원 데이터 없이 가상 사용자와 가상 인증 상태를 생성하고, 합성 테스트 SQL과 차별되는 **실제 구현 예정 PostgreSQL 함수 원본**을 일회용 환경에 설치. 실제 PostgREST/권한/세션/해당 구현 CAS 경합 및 rollback/redo 검사. 서버 DDL 대상은 운영 데이터가 아니라 **가상 DB에 한정**.
5. **운영 반영 전 별도 승인:** 최종 출시를 가정하더라도 운영 DB의 SQL 적용·main 반영·직원 데이터 수정은 별도 위험/복구 계획, 실증 결과와 명시적 사용자 최종 승인 없이는 수행하지 않는다. 기존 **RPC 계약 릴리스 RED 차단은 유지**.
